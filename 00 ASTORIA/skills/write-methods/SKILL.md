# Write Methods

Describe what was done or is proposed with enough precision to evaluate it.

## Purpose

Draft or revise a Methods section, a proposal's methodological passage, or a
technical procedure description from verified sources and specialist returns.
Keep procedure, rationale and status distinguishable. The domain owner chooses
and validates the work; this skill explains it faithfully.

## Inputs

Read the [writing contract](../writing-coordinator/references/writing_contract.md)
completely. Use the [cross-system handoff](../writing-coordinator/references/cross_system_handoff.md)
when domain-specialist material or requirements are involved.

Read the relevant MOC by the default in `me.md`, then the sections needed for
this assignment. Read any recipient-supplied writing guidance identified in the brief. If none is supplied, use the document-purpose and evidence requirements and the actual task sources. Writing preferences are not evidence for the project's scientific claims.

Recover the current writing brief: exact document/version, audience, section
purpose, central argument and its provisional or adopted status, any recipient-selected organizational requirements,
source locators, protected terminology, claim ceiling, required structure and
length, and authorized edits. Apply only a writing profile selected for this task or in the recipient's `me.md`. The available references include `writing-style-positive-scientific` and `writing-style-negative-ai`. Apply each independently when selected. Ask only for missing information that changes the
requested wording; continue unaffected work without inventing an answer.

Use the actual protocol, task/program configuration, scripts, analysis outputs,
records, and domain-translation packet needed for the passage. Obtain the
unit of analysis, actual or planned sample, conditions/outcomes, processing and
analysis specifications, and status of exclusions, QC and review. Use only
the applicable parts; a circuit, interview study and fMRI pipeline require
different details. A remembered software default is not project evidence.

## Steps

1. Identify whether each described action is planned, executed, technically
   checked, reviewed or adopted. Separate the proposed protocol from actual
   practice and reported deviations. For a proposal, use prospective wording;
   for completed work, verify actual settings rather than copying the plan.
2. Read the bounded primary records and domain-specialist return. Match the
   correct dataset/build, version and run/configuration to the document.
   Resolve discrepancies with the domain owner; do not rerun an analysis,
   redesign a circuit, choose exclusions or infer acceptance from file existence.
3. Lay out the procedure in the order the reader needs to reconstruct it.
   Use the supplied template when applicable. Explain the purpose and link
   to the question at the subsection level, preserving operational sequence.
   Explain consequential methodological choices where needed for reproducibility or interpretation; procedural descriptions do not require a paragraph framework.
4. Describe the actual system, participants/materials, recruitment or selection,
   conditions, apparatus/stimuli, timing, task, measurements and outcomes as
   applicable. Preserve values, units, coordinate/reference frames and labels.
   Distinguish what participants perceive, do and report; avoid generic
   phrases such as spatial judgment when a specific response is known.
5. Explain processing and analysis in a traceable sequence. Include applicable
   quality checks, exclusions, invalid/missing data handling, preprocessing,
   model specification, estimand/contrast, covariates, uncertainty, multiplicity,
   software/configuration and data/code availability from verified inputs.
   Name the operation and its input/output; software and model names alone
   do not describe what was estimated or tested.
6. For prediction or decoding, specify the target, feature source/time period,
   training/test partition and generalization test where supplied. Distinguish
   predicting a response from comparing activity periods or explaining a
   mechanism. Describe a planned validation as planned, not accomplished.
7. For engineering/technical procedures, retain the supplied component/net names,
   assembly orientation, dimensions, tolerances, configuration and recorded
   tests where relevant. Distinguish a verified digital result from physical
   performance, and a completed run from accepted QC or modeling readiness.
8. Explain equations only from the supplied model specification: name the
   quantities, their role and the question the comparison answers. Give an
   illustrative example only when requested or helpful, explicitly separating
   invented illustration from study values. Do not add a model to fill a gap.
9. Check the passage against applicable reporting requirements supplied or
   verified by their owner. Ask targeted questions for missing consequential
   parameters. Use placeholders only for a requested scaffold; do not replace
   absent detail with reassuring phrases such as standard procedures.
10. Read for reconstruction and argument linkage. The reader should understand
    both the operations and why they test the current question. Simplify
    sentence structure without deleting detail that determines the procedure.

## Outputs

Return the requested methodological prose, with brief targeted questions for
unresolved details. Preserve provisional status, deviations and claim limits.
For team work, return exact source locators for substantive facts through the
shared handoff; do not expose unnecessary raw records in the public prose.
Keep the canonical document with its assigned integration owner.

## Boundaries

- Do not invent sample/trial counts, timing, parameter values, power, calibration,
  ethics approval, apparatus access, QC decisions or successful validation.
- Do not turn a conventional default or specialist recommendation into an action
  that occurred. Do not certify reproducibility from a complete-looking section.
- Changing the outcome, model, comparison or procedure is a domain decision.
- Keep results and interpretation out of a procedural account unless the requested
  document type calls for them, and identify their role clearly.

## Handoffs

Use the cross-system handoff for missing technical inputs or a fidelity question
with the existing domain owner. Return prose to the invoking writing owner.
The substance checker checks content and specificity; the structure keeper
checks required coverage. The writer does not replace either independent review.

## Checks

- Can the reader identify the actions, inputs, outputs and relevant parameters?
- Do the described settings and status match the actual source version?
- Are planned, completed and reviewed work distinguishable?
- Are prediction targets and model comparisons defined rather than merely named?
- Does each rationale explain its bearing on the research/technical question?
- Are unresolved details visible rather than hidden by fluent prose?
