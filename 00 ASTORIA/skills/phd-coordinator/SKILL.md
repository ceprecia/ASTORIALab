# PhD Coordinator

Prepare concrete specialist assignments and collect their evidence inside the companion chat.

## Purpose

Operate internally in the lead PhD Companion chat. Ordinary academic and career mentoring can remain with the companion. Choose only skills relevant to the requested academic or career output; one worker is valid. A catalog mention is not a complete skill load or completed work.

## Inputs

Read the single shared naming registry at 00 ASTORIA/skills/research-coordinator/references/team_naming.md before names. Read current user scope, chosen MOC/config and current host project/chat inventory. For shared support discovery, use only the generated Skill Map's Capture and Writing Helpers group, then the selected helper's complete skill. For offline evaluation only, explicitly labelled mock host/source files replace those services; output planned dispatch records, never actual host calls.

## Steps

1. Resolve the work from the user's request and actual existing context. A missing fact blocks dependent work, not all unrelated work. Preserve settled project and scientific choices. Locate supplied inputs using bounded filename/link searches before declaring a dependency missing; the working folder alone is not the source inventory.
2. Resolve the exact installed skill from the generated catalog or shared support below. Do not claim a future/offered capability is installed. The assigned worker fully reads its skill, required guides and bounded sources; do not copy the full parent history or require the lead core in that worker.
3. Verify this lead chat's current project binding independently of source folders. Reuse appropriate authorized existing chats, preserving IDs and titles. Include archived/other-lane numbers when allocating project-wide max+1; reserve numbers centrally before parallel dispatch. Do not allocate persistent IDs when binding is unavailable. Use only registry prefixes and PREFIX-NN Role - Focus. A missing lane is a proposed registry change, not an improvised code.
4. If chat creation is not already authorized, have the companion ask one concrete scoped choice naming the specialists, verified project and goal, with dedicated chats recommended and internal workers as the alternative. Carry a scoped approval through kickoff, follow-ups and corrections without per-worker approval. Declined/unavailable chats or missing binding use internal skill-loaded workers; only unavailable worker tools or forbidden delegation uses a disclosed sequential fallback. Distinguish planned, created, running, needs-input, failed and verified-complete states. In simulation return proposed dispatch only. Actual execution, recording, saving, external contact and scheduling retain the current action scope.
5. Give each worker caller/return owner, project ID, exact skill/source paths (including current owner/profile evidence when relevant), concrete question, current facts/decisions, allowed actions, owned outputs, dependencies and completion evidence. Sequence dependent actions; parallelize isolated independent outputs. Keep one writer for a shared MOC/manuscript artifact.
6. Collect the completed result and verify its evidence and limits. A queue acknowledgment alone is not completion. Repair a discrepancy through its owner within existing scope. Do not launch critiques, searches, application submissions or saving merely because a worker returned.
7. On a stage change reuse relevant chats and update only affected assignments. Keep useful authorized role/skill/chat/scope/output/state mappings in existing AI Notes; prefixes stay in the single registry.

## Handoffs

Use writing-companion and its internal writing-coordinator for shared writing assistance, or an exact content-specific writer for a bounded section. Read `00 ASTORIA/skills/writing-coordinator/references/cross_system_handoff.md`; carry the current central claim/status, document purpose, source/profile/MOC locations and selected structure. Keep PhD Companion as original return owner, borrow scientific or technical review only when needed, and return any missing dependency once without recursive intake. Citation, substance, structure and argument-reasoning checks remain distinct roles. CV drafting and evidence records remain with research-cv-builder.

Use exact cross-system skills without copying them or loading every system. research-cv-builder remains one canonical capability. research-grant-advisor handles one selected application; opportunity discovery stays with phd-opportunity-scout. Use Research Companion only for scientific strategy outside the requested bounded service. Return to the invoking companion, preserving scientific ownership and source limitations. Never bounce a request back through an ancestor coordinator; return the missing dependency to its caller. No new application target/hypothesis or method is adopted by inference. Scope the service explicitly: a document-gap consult is not a full application or institutional readiness audit.

For structured handoffs, direction identifies the original consult request; preserve that direction and its owner/project identifiers in the return. Readiness status describes the requested application or dependency outcome, separately from completion of the worker consult.

## Shared support

Discover shared helpers through the generated Capture and Writing Helpers group; use their existing capture, protocol, transcript, handoff and redaction contracts without copying the catalog here. Chat Handoff prepares packets; it is not the live dispatcher. Preserve the user's current capture preference. Also borrow research-grant-advisor, study-companion, teaching-companion and woop-skill for their existing responsibilities. Shared writing specialists return through the original owner. For scientific interpretation or unsettled contribution choices, request a bounded Research Companion consult; obtain technical fidelity review from the relevant domain owner without routing every writing task through another full research session. Do not create copies or load these just because they are listed.

## Assignment and Return Format

Use a task-sized conversation record, omitting irrelevant fields:

```text
Caller, original return owner and verified current project: [...]
Exact installed skill and required guides: [...]
Concrete question, requested output and completion evidence: [...]
Bounded source paths, including the current owner/profile when relevant: [...]
Current decisions, known facts and unknowns not to infer: [...]
Authorized actions, owned outputs, dependencies and stop point: [...]
```

The worker reads its complete skill, required guides and supplied sources. Collect its actual result, sources/skills used, checks, limitations and state; return to the original owner. A missing dependency is a bounded return, not a fresh intake or recursive callback. Do not create tracking files for these records.
